# 本地算法沟通总纲：精简版

日期：2026-05-26

用途：把前面关于 SOC guidance、本地控制、优化维度、权重、目标函数的讨论收敛成一套能讲清楚的口径。

## 0. 云端现在已知的参数

云端不是只给 SOC guidance，而是已有/可提供一组半小时粒度的时间序列：

| 云端参数 | 含义 | 本地怎么理解 |
|---|---|---|
| 实际 EV 充电费用 | 车主充电带来的收入/收费结果 | 用于事后收益复盘，不建议本地实时直接优化 |
| 实际用电成本 | 场站从电网买电的实际成本 | 用于云端经济调度和事后复盘 |
| 预期负荷 | 云端预测未来半小时站内基础负荷/site load | 帮助解释为什么云端希望 SOC 高或低 |
| 预期 EV 充电量 | 云端预测未来半小时 EV 需求 | 帮助本地理解未来是否需要保电 |
| 预期 SOC | 云端希望未来 SOC 怎么走 | 本地的主要参考目标 |

这意味着：

> 云端负责维护这组费用、成本、负荷预测、EV 需求预测和预期 SOC 数据；本地负责在现场约束内执行对应策略，并在执行不了时回传原因。

本地可以额外做两件事：

1. 对比预测和实际：
   - 云端预期负荷 vs 实际 site load；
   - 云端预期 EV 充电量 vs 实际 EV 需求；
   - 云端预期 SOC vs 实际 SOC。

2. 回传偏差原因：
   - 车比预期多；
   - site load 比预期高；
   - 电池 SOC 太低；
   - 电网受限；
   - BMS/PCS 告警；
   - 车辆实际吃不下功率。

## 1. 最终不要讲成“全量动态权重优化”

前面写的公式是有用的，但它更适合作为“数学框架”，不适合一上来就说第一版要完整实现。

原因是：

- 经济调度里，费用、成本和价格是比较明确的输入，所以优化目标比较稳定；
- 本地控制里，现场状态一直在变，比如车什么时候来、车实际要多少功率、site load 多少、电池 SOC 多少、设备有没有告警；
- 所以 `w_ev / w_soc / w_bess / w_ramp / w_fair` 这些权重不应该一开始就假设是固定常数；
- 第一版如果直接讲动态权重，会显得太复杂，也很难解释这些权重从哪里来。

更好的说法是：

> 这个公式是用来表达本地算法会考虑哪些惩罚项，不代表第一版所有权重都已经确定。第一版先用场景化优先级，把不同现场情况分开，每个场景只抓一两个核心目标。

也就是说：

> 不是全局动态权重优化，而是“硬约束先筛掉不可行动作，场景决定优先级，目标函数只在可行动作里做局部选择”。

## 2. 最清楚的三层框架

最终建议按三层讲：

```text
第一层：硬约束
第二层：场景优先级
第三层：目标函数/惩罚函数
```

### 第一层：硬约束

这些东西不参与权重讨论，直接不能突破：

- BMS/PCS 严重告警；
- SOC 最低/最高边界；
- 电网最大取电功率；
- 单枪 160kW 上限；
- 电池最大充放电功率；
- 不能同时充电和放电；
- 云端 guidance 过期时不能继续按旧策略套利。

可以这样说：

> 硬约束先过滤掉所有不能执行的策略。安全、电网和设备边界不是靠权重平衡的，而是直接不可违反。

### 第二层：场景优先级

第一版不要做复杂动态权重，可以先按场景切换优先级。

| 场景 | 第一优先级 | 第二优先级 | 本地策略倾向 |
|---|---|---|---|
| 有车，SOC 安全，电网不够 | 减少 EV 充电缺口 | 尽量跟随 SOC | 电池可以补功率 |
| 有车，但 SOC 已经偏低 | SOC 保护 | 减少 EV 缺口 | 电池少放或不放 |
| 多车，资源不足 | 最低服务 + 公平性 | 总缺口最小 | 不让某一辆车长期很低功率 |
| 电网接近上限 | 电网不越限 | EV 缺口尽量小 | 电池补峰，补不了就降桩 |
| BMS/PCS 告警 | 安全保护 | 无 | 停止相关动作，回传原因 |
| 云端 guidance 过期 | 本地保守运行 | 现场供电 | 不做主动套利动作 |

可以这样说：

> 权重不是完全固定的，所以第一版先不用连续动态权重，而是用场景化优先级。不同场景下，主目标不同。

### 第三层：目标函数/惩罚函数

在某个场景里，如果有多个可行策略，再用简单的惩罚函数打分。

```text
min J =
  w_ev   * EV_充电缺口
+ w_soc  * SOC_偏离云端参考
+ w_grid * 电网越限惩罚
+ w_bess * 电池使用/寿命惩罚
+ w_ramp * 功率波动惩罚
+ w_fair * 多车公平性惩罚
```

但要强调：

> `J` 不是电费成本，而是综合不满意分。第一版不一定全部实现，只是说明这些是本地策略可能要扣分的地方。

## 3. 第一版到底做什么

第一版建议做：

1. 明确硬约束：
   - 电网不能越限；
   - SOC 不能越界；
   - BMS/PCS 告警必须保护；
   - 单枪不能超过 160kW。

2. 明确几个主要场景：
   - 单车充电；
   - 多车充电；
   - SOC 偏低；
   - site load 偏高；
   - 电网受限；
   - 设备告警；
   - 云端 guidance 过期。

3. 每个场景只定一两个主目标：
   - 正常有车时，优先减少 EV 充电缺口；
   - SOC 偏低时，提高 SOC 保护优先级；
   - 多车时加入最低服务和公平性；
   - site load 高时，优先防止超容，可以用 BESS 支撑或降低 EV；
   - 电网受限时，先保证不越限。

4. 回传原因：
   - 为什么没跟随云端 SOC；
   - 为什么没给满车的功率；
   - 是因为电网、电池、SOC、告警、还是车本身吃不下。

第一版不建议做：

- 不做完整动态权重优化；
- 不承诺全局最优；
- 不把 ChatGPT/LLM 放进实时控制闭环；
- 不把复杂电价套利放在本地第一版主目标里。

## 4. 你可以直接对 Ning 说的版本

> 我重新收敛了一下。前面那个目标函数主要是表达本地算法可能考虑哪些惩罚项，不代表第一版所有权重都已经确定。云端现在有实际 EV 充电费用、实际用电成本、预期负荷、预期 EV 充电量和预期 SOC，这些更适合在云端做半小时级经济调度。本地控制这里面对的是实时车流、site load、实际充电需求、电池 SOC、设备告警，所以不应该一上来把所有权重写死。
>
> 所以我建议第一版不要直接做全量动态权重优化，而是分三层：第一层是硬约束，安全、电网、SOC、PCS、单枪上限这些不能突破；第二层是场景优先级，比如有车且 SOC 安全时优先减少 EV 充电缺口，SOC 偏低时优先保护 SOC，多车时考虑最低服务和公平性；第三层才是在可行策略里用一个简单的惩罚函数打分，比如 EV 缺口、SOC 偏离、电池使用、功率波动这些。
>
> 这样第一版会更容易落地：先把硬约束、典型场景、主目标和偏离原因回传打通，后面有测试数据之后再逐步调整权重或做更复杂的优化。

## 5. 如果他问“权重怎么来”

可以回答：

> 第一版我不建议假设这些权重已经精确可得。更现实的做法是先按业务优先级和场景规则给初始逻辑，比如正常有车时 EV 缺口优先，SOC 偏低时 SOC 保护优先，电网接近上限时电网约束优先。等测试环境有数据后，再通过回放和 KPI 去调权重。

再补一句：

> 所以现在这个数学框架不是在说权重已经定好了，而是在说我们未来可以把哪些目标量化进去。

## 6. 一句话总结

> 第一版不是做复杂动态权重优化，而是先做“硬约束 + 场景优先级 + 简单目标函数”，把本地策略能解释、能验证、能回传原因这件事打通。
