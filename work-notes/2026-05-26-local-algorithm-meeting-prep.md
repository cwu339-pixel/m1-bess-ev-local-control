# 本地算法优化维度沟通准备

日期：2026-05-26

用途：和 Ning 沟通本地算法优化维度。目标不是证明已经有最终算法，而是把“云端 SOC guidance 到本地策略输出”中间需要考虑的维度、控制点、限制点、目标函数和验证案例讲清楚。

## 0.1 云端现在已知的参数

子睿/云端可以提供半小时粒度时间序列：

| 参数 | 含义 | 对本地的作用 |
|---|---|---|
| 实际 EV 充电费用 | EV 充电收入/收费结果 | 用于收益复盘，不建议本地实时直接优化 |
| 实际用电成本 | 场站买电成本 | 云端经济调度依据，本地可用于事后解释 |
| 预期负荷 | 未来半小时 site load 预测 | 判断未来电网压力和是否需要保 SOC |
| 预期 EV 充电量 | 未来半小时 EV 需求预测 | 判断未来车辆需求和储能支援需求 |
| 预期 SOC | 云端希望 SOC 怎么走 | 本地主要参考目标 |

可以这样讲：

> 这些参数说明云端不是只给 SOC guidance，而是会有一组半小时粒度的时间序列参数。经济性、预测和预期 SOC 主要在云端；本地不重新做完整经济调度，而是在现场实时约束内用这些参数里和 M1 相关的部分，尤其是预期 SOC/SOC band，去决定本地动作。如果执行不了，本地回传实际负荷、实际 EV 需求、实际 SOC 和偏离原因。

## 0. 先背这一版口径

如果只讲 2-3 分钟，可以这样说：

> 我现在的理解是，云端会给半小时粒度的 SOC guidance，本地不是直接照抄这个 SOC，而是把它作为参考目标。真正落地时，本地还要看现场有没有车、车要多少功率、电网还能给多少、电池当前 SOC 和可充可放能力、BMS/PCS/充电桩有没有告警，最后输出具体策略。
>
> 所以我这版先不是写最终算法，而是把本地算法可能考虑的维度拆出来。主要分四类：第一是用户和运营体验，比如单车速度、充电缺口、多车公平；第二是数学优化目标，把这些取舍写成目标函数；第三是硬约束和风险，比如 SOC 上下限、BMS 告警、电网容量、PCS 上限，这些不能突破；第四是云端和本地接口，云端给什么、本地回什么、怎么解释偏离。
>
> 第一版我建议：安全红线先过滤掉不可行策略；在安全可行的范围内，优先减少 EV 充电缺口，同时尽量跟随云端 SOC guidance。如果本地因为车太多、电网限制、电池 SOC 低、BMS 告警而没有跟随云端，就把偏离原因回传给云端。

## 1. 开场怎么说

可以这样开场：

> 我这边先按本地算法的角度整理了一版。现在理解是：子睿那边云端会输出半小时粒度的 SOC guidance，本地不会直接照抄这个 SOC，而是把它作为参考目标，再结合现场实时状态，最后输出本地策略。
>
> 所以我现在不是先写死一条规则，而是先把本地算法会影响策略的维度尽可能列全。后面我们再一起讨论第一版应该优先保哪些目标，哪些作为硬约束，哪些先放到后续版本。

再补一句：

> 我参考了一些储能 EMS、本地能量管理、EV 充电功率分配和云边协同控制的思路。整体结论是，这类问题一般不会只用一个 SOC 目标直接决定动作，而是会分层处理：先看安全和设备边界，再看现场车辆需求和电网能力，再看云端 SOC guidance，最后输出本地功率策略。

## 2. 我们最后要解决的问题

一句话：

```text
云端给半小时 SOC guidance；
本地结合车、电网、电池、安全状态；
在硬约束内输出充放电和充电桩功率策略。
```

本地策略可能包括：

- 电池放电、不放电、充电；
- 电池放多少 kW；
- 充电桩总功率给多少；
- 多车时每台车分多少；
- 是否限功率；
- 如果偏离云端 SOC guidance，为什么偏离。

## 2.1 本地控制点和限制点

Ning 如果问“本地到底能控制什么”，可以这样分。

本地能控制的点：

| 控制点 | 具体含义 |
|---|---|
| 充电桩功率 | 每个枪/每台车允许多少 kW，是否降功率、暂停、恢复 |
| 电池 PCS | 电池充电功率、放电功率、待机、限功率、紧急停机 |
| 站内功率分配 | 车优先、电池补峰、电网限额、多车功率分摊 |
| SOC guidance 执行 | 把云端半小时 SOC_ref 当作参考，不是无条件命令 |
| 本地保护动作 | 报警时降额或停机，通信异常时进入保守策略 |
| 电网侧控制 | 限制总取电功率，必要时防反送，避免超过并网容量 |

本地不能突破的限制点：

| 限制点 | 具体含义 |
|---|---|
| 电网硬上限 | 并网点最多只能取多少 kW，本地 EMS 不能突破 |
| 车端限制 | 车实际能吃多少功率由车的 SOC、温度、电池状态决定 |
| 充电桩上限 | 单枪最高 160kW，不能突破枪线和设备能力 |
| 电池硬约束 | SOC 上下限、最大充放电功率、温度、SOH、PCS 容量 |
| 安全报警 | 消防、绝缘、过温、BMS fault、PCS fault、急停等优先级最高 |
| 通信/数据质量 | 云端 guidance 过期、表计异常、车桩通信异常时不能冒险控制 |
| 并网规则 | 是否允许反送电、功率爬坡率、需量限制、保护定值 |

优先级可以这样讲：

```text
报警/急停
> 电网容量
> 设备功率/SOC/温度
> 车端需求
> 云端 SOC guidance
```

## 3. 四个核心维度

这次我建议从四类维度发散：

| 维度大类 | 回答的问题 | 可以放进去的内容 | 对策略的影响 |
|---|---|---|---|
| 用户/运营体验维度 | 车主和站点希望什么结果 | 单车充电速度、充电缺口、完成时间、等待时间、多车公平性、最低服务保障 | 决定是否优先让车充得快，是否保证每台车最低功率，是否公平分配 |
| 数学优化目标维度 | 如果目标冲突，用什么标准选策略 | 最小化 EV 充电缺口、最小化 SOC 偏离、最小化电网越限、最小化电池使用、最小化功率波动 | 把业务目标变成可计算的目标函数 |
| 硬约束/风险维度 | 哪些东西绝对不能突破 | SOC 上下限、BMS 告警、PCS 功率上限、电网限制、单枪上限、温度、通信过期、不能同时充放电 | 决定哪些策略直接不可行，不参与优化讨论 |
| 云端-本地接口维度 | 云端给什么，本地回什么，怎么验证 | SOC guidance、有效期、允许偏差、电网限制、本地动作、SOC 偏差、EV 缺口、偏离原因 | 决定本地怎么理解云端，以及怎么回传给云端复盘 |

可以这样总结：

```text
用户/运营体验：我们想要什么结果
数学优化目标：怎么把这些结果写成公式
硬约束/风险：哪些边界绝对不能破
云端-本地接口：云端给什么，本地怎么执行和回传
```

## 3.1 云端和本地接口要对齐什么

云端建议给本地的字段：

| 字段 | 用途 |
|---|---|
| `site_id / asset_id` | 标识站点、电池、PCS、桩群 |
| `schedule_version` | 版本号，便于回滚和对账 |
| `valid_from / valid_to` | 生效时间，避免使用过期 guidance |
| `interval_start / interval_end` | 半小时粒度时间窗 |
| `soc_guidance_min / soc_guidance_max` | 建议 SOC 区间，更适合本地模糊调度 |
| `soc_target_preferred` | 云端建议目标 SOC |
| `charge_power_limit_kw / discharge_power_limit_kw` | 云端建议功率边界 |
| `priority / confidence` | 建议优先级和置信度 |
| `reason_code` | 云端为什么给这个 SOC，例如电价、负荷预测、备用容量、峰值控制 |
| `fallback_policy` | 云端失联或版本过期时，本地怎么做 |

本地建议回传云端的字段：

| 字段 | 用途 |
|---|---|
| `actual_soc` | 实际 SOC |
| `actual_charge_power_kw / actual_discharge_power_kw` | 电池实际充放电功率 |
| `ev_power_kw` | EV 实际总功率 |
| `power_gap_kw` | EV 充电缺口 |
| `executed_strategy` | 本地实际执行策略 |
| `guidance_accepted` | 是否接受云端 guidance |
| `override_reason` | 本地为什么覆盖云端建议 |
| `safety_events / alarms` | 告警和安全事件 |
| `data_quality` | 数据是否完整、延迟、异常 |
| `kpi_summary` | SOC 偏离、未满足需求、削峰效果等 |

## 4. 数学公式怎么讲

不要说“电费成本”，这里的 cost 不是价格成本，而是优化里的“惩罚”。

可以说：

> 这里的 J 不是电价成本，而是总惩罚函数。它表示一个策略整体有多不好。比如车没充够、SOC 偏离云端、电网超限、电池使用太猛、功率跳动太频繁、多车分配不公平，这些都是我们不希望发生的事情。算法就是在所有可选策略里，找一个总惩罚最小的策略。

更口语一点可以说：

> 安全红线先过滤掉不能做的动作；剩下的动作再用 J 打分；min J 就是选综合不满意分最低的那个动作。

公式：

```text
min J =
  w_ev   * EV_充电缺口
+ w_soc  * SOC_偏离云端参考
+ w_grid * 电网越限惩罚
+ w_bess * 电池使用/寿命惩罚
+ w_ramp * 功率波动惩罚
+ w_fair * 多车公平性惩罚
```

每一项的人话解释：

| 项 | 人话解释 | 希望结果 |
|---|---|---|
| EV 充电缺口 | 车想要 150kW，实际只给 100kW，缺口就是 50kW | 越小越好 |
| SOC 偏离云端参考 | 云端希望 70%，实际 60%，偏离就是 10% | 越小越好，但这是软目标 |
| 电网越限惩罚 | 电网最多 100kW，策略却要 120kW，越限 20kW | 最好为 0，通常做硬约束 |
| 电池使用/寿命惩罚 | 不要无脑高功率充放电、频繁充放电 | 越少越好 |
| 功率波动惩罚 | 不要一会儿 150kW，一会儿 80kW | 越平滑越好 |
| 多车公平性惩罚 | 不要长期让一台车吃满，另一台车很低 | 越公平越好 |

`w` 是权重参数，不是要最小化的东西。它表示每个目标有多重要。

第一版可以先这样设方向：

```text
硬约束最高优先级；
w_ev 最大，优先减少 EV 充电缺口；
w_soc 中等，SOC 跟随云端但允许偏离；
w_bess、w_ramp、w_fair 先作为次级目标。
```

## 5. 一个具体案例怎么讲

案例输入：

```text
云端 SOC_ref = 70%
车请求功率 = 150kW
现场单枪上限 = 160kW
电网最大可用功率 = 100kW
电池最大可放电功率 = 50kW
```

这个输入本身不会自动决定唯一策略，要看我们优先什么：

| 优先维度 | 可能策略 | 解释 |
|---|---|---|
| 单车充电速度优先 | 电网 100kW + 电池 50kW，车拿到 150kW | 用户体验最好，但 SOC 会下降 |
| SOC 跟随优先 | 如果当前 SOC 已低于 70% 或接近下限，电池少补或不补 | 保护云端 SOC 参考，牺牲部分充电速度 |
| 电池寿命优先 | 电池不一定补满 50kW，可能只补 20-30kW | 避免长期高功率放电 |
| 多车公平性优先 | 多车时总功率按规则分配 | 不让一台车吃满，另一台车长期不足 |
| 硬约束优先 | BMS 告警、SOC 过低、电网超限时直接限制 | 安全高于所有目标 |

重点：

> 不是电池一定补 50kW，而是根据我们选择的优化维度和硬约束，输出最合理的本地策略。

## 6. 四个测试案例

### 案例 1：单车速度优先

```text
SOC_ref = 70%
当前 SOC = 75%
一辆车请求 = 150kW
电网可用 = 100kW
电池最多可放 = 50kW
无告警
```

预期：

```text
电网给 100kW
电池补 50kW
车实际拿到 150kW
```

验证点：SOC 安全、电池可放时，优先减少 EV 充电缺口。

### 案例 2：SOC 保护优先

```text
SOC_ref = 70%
当前 SOC = 45%
一辆车请求 = 150kW
电网可用 = 100kW
电池最多可放 = 50kW
无告警
```

预期：

```text
电网给 100kW
电池少补，比如 0-20kW
车实际拿到 100-120kW
```

验证点：不是所有时候都补满。当前 SOC 已明显低于云端参考时，要减少放电。

### 案例 3：多车公平性

```text
SOC_ref = 70%
当前 SOC = 75%
车 A 请求 = 160kW
车 B 请求 = 160kW
电网可用 = 160kW
电池最多可放 = 60kW
总可用 = 220kW
总请求 = 320kW
无告警
```

一种预期：

```text
车 A = 110kW
车 B = 110kW
```

而不是：

```text
车 A = 160kW
车 B = 60kW
```

验证点：如果考虑公平性，就不能只最大化某一台车速度。

### 案例 4：硬约束触发

```text
SOC_ref = 70%
当前 SOC = 80%
一辆车请求 = 150kW
电网可用 = 100kW
电池最多可放 = 50kW
但 BMS 告警 / PCS 故障 / SOC 数据过期
```

预期：

```text
禁止电池放电
电网最多给 100kW
车实际拿到 100kW
回传原因：BMS/PCS/数据异常导致无法补足 EV 缺口
```

验证点：硬约束不是权重问题，是直接不能突破。

## 6.1 运营功率分配补充案例

这几个案例适合回答“单车最快”和“全站缺口最小”有什么区别。

| 场景 | 输入 | 更合理的策略 | 说明 |
|---|---|---|---|
| 单车且资源充足 | 一辆车请求 160kW，站点功率充足 | 给 160kW | 没有资源冲突时，可以最大化单车速度 |
| 两车都要 160kW，站点只有 160kW | A=160kW，B=160kW，总可用=160kW | 可以各 80kW，或按等待时间/运营优先级分配 | 不应长期 A=160kW、B=0kW |
| A 要 160kW，B 要 60kW，站点只有 160kW | A=160kW，B=60kW，总可用=160kW | B=60kW，A=100kW | 先满足真实低需求车，剩余给高需求车，比简单平均更合理 |
| A 请求 160kW 但实际只吃 70kW，B 请求 120kW | 总可用=160kW | A=70kW，B=90kW | 用实际吸收功率反馈修正，避免功率浪费 |

## 7. Ning 可能会问的问题

### Q1：云端给的是 SOC 点还是 SOC 区间？

建议回答：

> 第一版我理解可以先支持一个半小时粒度的 SOC_ref；如果云端能给区间，比如 SOC_min/SOC_target/SOC_max，会更适合本地模糊调度。因为本地不一定能精确追到一个点，给区间会更合理。

### Q2：本地偏离云端 SOC 怎么办？

建议回答：

> 偏离本身不一定是错。关键是偏离要有原因，比如 EV 需求太高、电网限制、SOC 下限、BMS 告警、云端 guidance 过期。本地需要把偏离值和原因回传给云端。

### Q3：最大化单车充电速度和最小化 EV 充电缺口有什么区别？

建议回答：

> 单车速度是用户体验维度，关注某一辆车现在充得快不快。EV 充电缺口是数学目标，关注请求功率和实际功率之间差多少，更适合作为全站调度目标。多车时还需要公平性约束，避免一辆车吃满、另一辆车长期不足。

### Q4：车想要多少功率怎么知道？

建议回答：

> 优先用车桩握手或充电桩侧请求功率；如果第一版拿不到，就先用单枪上限 160kW 作为需求上限，再用实际吸收功率反馈修正。这样不会把车本身吃不下功率误判成本地策略没满足。

### Q5：电网越限是目标函数还是硬约束？

建议回答：

> 实际控制里应该优先当硬约束，不能突破。放进目标函数里是为了表达“越限惩罚极高”，但第一版实现时可以直接写成边界条件。

### Q6：ChatGPT/LLM 能不能作为云端一部分？

建议回答：

> 可以作为云端辅助分析层讨论，但不应该进入实时控制闭环。它可以辅助做维度发散、测试案例生成、日志复盘、偏离原因解释；但不直接输出电池和充电桩的实时功率指令。

### Q7：第一版要不要考虑电价套利？

建议回答：

> 第一版可以先不把复杂套利作为主目标。先把本地安全、EV 缺口、SOC 跟随、接口闭环打通。电价套利可以后续通过云端 SOC guidance 间接体现。

### Q8：云端已经给 SOC guidance，本地为什么还需要目标函数？

建议回答：

> 云端是半小时级别的方向，本地面对的是实时车辆、电池、电网和安全状态。目标函数的作用是把云端建议和现场状态结合起来，做实时取舍。

### Q9：本地目标第一优先级是什么？

建议回答：

> 安全不是普通优先级，而是硬约束，必须先满足。在安全可行之后，第一版可以把减少 EV 充电缺口作为主目标，SOC guidance 作为软目标去跟随。

### Q10：这些权重怎么定？

建议回答：

> 先按业务优先级给初值：安全红线单独处理，车的充电满足度优先，然后是云端 SOC 跟随、电池保护、功率平稳。后面用典型场景回放调权重，不需要一开始追求完美。

### Q11：电池补 50kW 是固定的吗？

建议回答：

> 不是。50kW 只是当前条件允许时的可用补能能力。实际要看电池 SOC、温度、BMS 限制、PCS 状态、报警和站内功率需求。

### Q12：怎么保证不会超过电网 100kW？

建议回答：

> 本地 EMS 实时读并网点表计，把 100kW 当作硬上限。如果车侧负载上升，先调用电池补峰，补不了就降充电桩功率。

### Q13：公平是不是平均分？

建议回答：

> 不是。公平不是每辆车永远一样多，而是按真实需求、车辆可吸收能力、等待时间和最低服务保障来分。比如一辆车只请求 60kW，就不需要硬分 80kW，多出来应该给更需要的车。

### Q14：运营上怎么判断算法好不好？

建议回答：

> 看几个指标：全站有效输出功率高不高、EV 充电缺口小不小、最低服务有没有保障、有没有车长期低功率、SOC 有没有合理跟随云端、有没有违反硬约束。

### Q15：云端给的是命令还是建议？

建议回答：

> 是半小时粒度的 SOC guidance，不是实时控制命令。本地根据现场状态、设备约束和安全规则决定是否执行、如何执行。

### Q16：怎么验证云端 guidance 有没有价值？

建议回答：

> 可以先做离线回放和 shadow mode，对比有无 guidance 下的 SOC 偏离、EV 缺口、峰值、电池使用、约束违规次数。再小范围上线，看本地接受率、覆盖原因和实际 KPI。

### Q17：云端失联怎么办？

建议回答：

> 本地必须有 fallback policy。可以继续执行最近一个未过期版本，或切到本地保守策略。云端 guidance 必须带 valid_to，过期后不能盲目继续执行。

### Q18：ChatGPT/LLM 会不会影响实时控制安全？

建议回答：

> 不会。LLM 不在实时控制路径里，不直接控制设备。它只适合做解释、日志复盘、测试案例生成、会议材料和异常原因分析。真正执行逻辑还是由本地 EMS 和确定性规则负责。

## 8. 表达风险：这些话不要说

| 不要这样说 | 应该这样说 |
|---|---|
| 云端 SOC 是命令 | 云端 SOC 是 guidance/参考目标 |
| 本地一定追到 70% | 本地尽量跟随 70%，但允许因为现场约束偏离 |
| 车要 150kW，我们一定给 150kW | 在电网、电池、安全条件允许时尽量满足 |
| 电池一定补 50kW | 50kW 是可用补能能力，不是固定动作 |
| 安全也可以通过权重 trade off | 安全是硬约束，不参与权重折中 |
| min J 是最小化电费成本 | min J 是最小化综合不满意分/总惩罚 |
| 我们已经有最终算法 | 现在是维度和框架对齐，后续再定第一版实现 |
| ChatGPT 可以控制电池 | ChatGPT 只能做辅助分析，不进入实时控制闭环 |

## 9. 你最后可以怎么收尾

可以这样说：

> 所以我这版不是最终算法，而是先把本地算法可能受影响的维度整理出来。我的建议是第一版先定一个简单主线：硬约束不能破，在安全范围内优先减少 EV 充电缺口，同时把 SOC guidance 作为软约束去跟随。每次本地没有跟随云端时，都要能回传偏离原因。这样后面无论云端模型怎么优化，本地都有一个比较清晰的执行和验证框架。
